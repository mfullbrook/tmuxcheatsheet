## Problem Statement

tmuxlab v1 (built 2026-07-05) is a complete tmux cheat sheet + tutorial + config generator: 58 static pages, tmux-native keyboard UX, an interactive playground, and content targeting the top researched pain points. It is better than the incumbents on fundamentals — but "better fundamentals" is not a launch story. The goal is the definitive free tmux resource, launched r/tmux → Show HN, and that needs one feature nobody else has and no one can copy in a weekend.

The gap, from the pain-point research: every tmux reference documents *default* tmux, but tmux users customize aggressively (oh-my-tmux: 25k stars), and the recurring meta-complaint is "snippets and cheat sheets online don't match my setup." The man page already documents defaults. Nothing documents *your* tmux.

## What Makes This Cool

Paste your `.tmux.conf` and the entire site re-renders with **your** bindings — cheat sheet, search palette, command pages. A one-click **"your keys / default keys"** toggle solves the real tension the research surfaced (custom config at home vs. default muscle memory on servers). And the same parser powers **"Explain my tmux.conf"**: paste a config, get a line-by-line annotated explanation with stale-advice warnings. That page is itself a shareable artifact: "I pasted my 8-year-old config and it told me what's obsolete."

v1's prefix picker was the seed of this; this is the full tree.

## Constraints

- Free, open source (MIT), no ads. Next.js on Vercel, fully static — parsing must be 100% client-side (no server, no config leaves the browser; that's also the privacy story for the launch post).
- Zero runtime dependencies policy from v1 holds: the parser is hand-written, not a grammar library.
- Site must remain fully functional with no config pasted (defaults = current behavior). Parser code is lazy-loaded; zero cost for visitors who never paste.
- Launch blockers outside this feature: domain/brand decision (currently placeholder "tmuxlab / tmuxlab.dev" in layout.tsx, sitemap.ts, robots.ts, llms.txt) and Vercel deploy. GitHub repo goes public at the r/tmux moment.

## Premises (agreed)

1. Config-awareness is the right next build — not more content, not a WASM terminal. Without it, the launch story is "nicer tmuxcheatsheet."
2. The parser is a **reader, not an interpreter**, with an explicit contract (below). Unrecognized lines are skipped and surfaced ("couldn't read these N lines"), never an error wall.
3. This is a data-layer overlay on v1's existing typed model (lib/data/keybindings.ts, KeyboardProvider prefix context, KeyCombo) — plus one new module the overlay depends on: a tmux-command normalizer (see Build order step 2).
4. Launch sequence: domain + deploy → r/tmux soft launch (which stress-tests the parser on real configs) → Show HN with config-awareness as the headline.

## Parser Contract (the exact whitelist)

**Evaluation model:** the parser emits an **ordered event list** applied in source order with last-wins semantics (tmux's own behavior): `unbind C-b` followed later by `bind C-b …` yields a live binding; a duplicate `set -g prefix` takes the last value. The resolved result — maps keyed by `(table, canonical key)`: `{prefix, bindings: Map, unbinds: Set, options: Map, warnings[], skipped[]}` — is computed from that event stream, never from unordered collection (build step 1 returns exactly this shape).

**Parsed and applied to site rendering:**
- `set -g prefix <key>` (single prefix only; `prefix2` is out of scope v1 — recognized, listed in "other settings," not rendered in KeyCombo)
- `bind`/`bind-key` and `unbind`/`unbind-key` in tables `prefix`, `root` (`-n`), and `copy-mode-vi` — including `-r`. A `bind` whose command is a `{ … }` brace block (tmux ≥ 3.0) is captured via brace-matching in the tokenizer and rendered as a custom binding labeled "command block (not interpreted)" — never a tokenizer error.
- `unbind -a [-T table]`: **recognized with a warning, not applied** — minimal-rebind configs would otherwise strike out the whole sheet; the explain page notes "this config unbinds all defaults; strike-through shown only for explicitly unbound keys."
- Rendering-affecting options, exact list: `prefix`, `mode-keys` (`vi` overlays copy-mode-vi; `emacs` triggers a visible note — "your copy mode is emacs; copy-mode section shows vi defaults" — and emacs table bindings fall to skipped-with-count). `mouse` is annotation-only (nothing on the site renders differently).
- `set` forms accepted for all whitelisted option names: `set`, `set-option`, `setw`, `set-window-option`, with `-g`, `-s`, `-w`, `-q` in any combination. `-a`/`-ga` (append) is recognized and annotated "appended (not merged)" — the value is not merged.
- Command chains (`… \; …`): parse the **first** command, annotate "+N chained commands." The reload idiom (`source-file … \; display …`) overlays the reload-config entry with annotation "also displays a message."

**Parsed for annotation only (shown in explain + "other settings", no rendering change):**
`base-index`, `pane-base-index`, `renumber-windows`, `history-limit`, `escape-time`, `focus-events`, `default-terminal`, `set-clipboard`, `status-position`.

**Recognized for warnings/annotation only (not interpreted):**
- Legacy `bind -t vi-copy|emacs-copy` syntax (pre-2.4)
- `mode-mouse` / `mouse-select-pane` / `mouse-resize-pane` / `mouse-select-window` (pre-2.1)
- `run-shell … reattach-to-user-namespace` / `default-command … reattach-to-user-namespace`
- `terminal-overrides` and `terminal-features` (feed stale-advice rule 5; values echoed, not interpreted)
- Styling options the generator itself emits (`status-style`, `status-left`, `status-left-length`, `status-right`, `window-status-current-style`): annotated as "status styling (not interpreted)"
- `@`-prefixed plugin options and `set -g @plugin` lines: grouped under "plugin settings"

**Skipped with count + line references:** `if-shell`, hooks, `%if` blocks, standalone format strings, `display-menu`/`display-popup` bodies, everything else.

**Also in the bind grammar:** `-N "note"` (tmux ≥ 3.1) is consumed as a valued flag (note surfaced in explain output); `set -u`/`-gu` on whitelisted options is recognized and applied in the event stream (unset → back to default). A `source-file` line triggers a prompt on the explain page: "this config sources `<path>` — paste that file too for full coverage" (critical for gpakosz-style configs that keep customization in `.tmux.conf.local`).

**Normalization rules (part of the contract):**
- Keys: canonical tmux notation — `^B`→`C-b`, `M-`/`Meta` unified, quoted keys unquoted, case preserved as tmux treats it; identity is `(table, canonical key)`.
- Commands: alias expansion (`splitw`→`split-window`, `selectp`→`select-pane`, …) via an alias table produced by a **dev-time script from `tmux list-commands` output and committed as `lib/config-parser/aliases.ts`** (it does not exist yet; it is step 2's first task).
- Copy-mode tables: the `send-keys -X <action>` wrapper is stripped so user bindings compare against bare copy-mode actions (`begin-selection`, `copy-pipe-and-cancel`, …), matching how the dataset stores them.
- **Flag matching rule:** a user binding matches a dataset entry when commands are equal after alias expansion AND the dataset entry's flag set is a **subset** of the user's flag set. Flag identity = flag name **plus argument** for valued flags: `-c "#{pane_current_path}"` is one member (unmatched extra → annotated "+ opens in current directory"); `-l 30%` vs `-l 50%` are different members (annotated, still a match if the dataset entry has no `-l`). Directional variants (`-U/-D/-L/-R`) match per-flag. No subset match → "Your other bindings."
- **Both sides normalize:** dataset entries gain machine-readable match fields (see build step 0) that run through the same pipe as user input; a dev-time test asserts every dataset match field normalizes cleanly.

## Stale-Advice Rules (launch set — 6, high-confidence only)

1. `reattach-to-user-namespace` → unnecessary since tmux 2.6 (2017)
2. `default-terminal "screen-256color"` (or `screen`) → suggest `tmux-256color` (italics, modern features)
3. `bind -t vi-copy/emacs-copy …` → pre-2.4 syntax, silently dead on modern tmux; link the migration
4. `mode-mouse` / `mouse-select-*` / `mouse-resize-*` → pre-2.1; it's just `set -g mouse` now
5. `terminal-overrides ",*256col*:colors=256"` presented as a true-color fix → 256 indexed ≠ RGB; suggest `terminal-features ",*:RGB"` (info-level, not error)
6. `history-limit` ≥ 500000 → RAM-per-pane warning; suggest `pipe-pane` logging instead (info-level)

Each rule links to the existing guide/command page that explains it. More rules post-launch as real configs surface patterns.

## Approaches Considered

### Approach A: Overlay — "your keys everywhere" (M effort, low risk)
Client-side parser → override map in localStorage → KeyCombo/cheat sheet/palette render custom keys with a defaults toggle. Site-wide payoff, no new pages, quiet "whoa" (no shareable artifact). Reuses the keybinding dataset, prefix context, and KeyCombo.

### Approach B: Config as first-class data (L effort, medium risk)
Everything in A plus playground rebinding, a "what you changed" diff view, and configs compressed into shareable URL hashes. The complete vision, but delays launch and multiplies edge cases (URL-encoded configs become a support surface).

### Approach C: "Explain my tmux.conf" front door (M effort, low risk)
A standalone tool page: paste → annotated line-by-line explanation, links into existing guides/command pages, stale-advice warnings. Launch-worthy artifact on its own; annotation content half-exists in v1's guides. Without A, though, it's a tool rather than a transformed site.

## Recommended Approach

**A + C staged, sharing one parser. B's shareable-URL piece is deferred until after launch.**

Rationale: A delivers the site-wide transformation ("this is *my* tmux"), C gives r/tmux a concrete reason to paste real configs — which QA's the parser on real-world input for free — and together they are less work than B alone.

Build order:
0. **Dataset match-schema pass** (`lib/data/keybindings.ts`): the dataset stores display strings — grouped keys like `"↑ ↓ ← →"` and synthetic commands like `select-pane -U/-D/-L/-R` — which cannot participate in matching. Add machine-readable `matchKeys: string[]` and `matchCommands: string[]` fields alongside the display fields (display rendering unchanged; grouped rows enumerate their real keys/commands in the match fields). This is the schedule risk item — it touches all ~80 entries and sits on the critical path (see Reviewer Concerns).
1. **Parser core** (`lib/config-parser/`): line tokenizer implementing the Parser Contract above → the resolved-maps shape defined in the Evaluation model. Test fixtures from ~10 real-world configs. Handles quoting, comments, brace blocks, `\;` chains per contract. Includes test-infra setup — the repo currently has no test runner; add vitest as a dev dependency in this step.
2. **Command normalizer** (`lib/config-parser/normalize.ts`): alias table (dev-time script from `tmux list-commands` → `aliases.ts`) + flag matching per contract + key canonicalization, with its own fixture tests. This is the load-bearing module — mapping `bind '"' splitw -v` onto the dataset's `split-window` entry is the hard half of the feature, and every downstream step depends on it.
3. **Shared option docs** (`lib/data/option-docs.ts`): extract the generator's inline comment strings into an option→explanation map consumed by both ConfigGenerator and the explain page (small refactor of `generate()`).
4. **ConfigContext** (extends KeyboardProvider): parsed overrides + source text in localStorage under one new key; the legacy `tmux-prefix` key migrates into it on first load and is removed. Precedence: pasting a config **replaces** the whole ConfigContext; the prefix picker **writes through** to ConfigContext.prefix; the your-keys/defaults toggle is a UI preference persisted under its own key (survives navigation and sessions) and never mutates the stored config. A "clear config" control resets to defaults and wipes storage. **Hydration:** pages SSR with default keys; overrides apply after hydration — for the small population with a stored config we accept a single key-text swap on load (acceptable reflow; give `<kbd>` a min-width so short↔long prefix swaps don't jitter), keeping content pages zero-JS-cost for everyone else.
5. **/config/explain page** (Approach C): paste box → annotated view. Per line: parsed meaning (from dataset labels + option-docs), warnings (rules above), or honest "not annotated" grouping for skipped lines with a count. CTA: "apply to the whole site" (feeds ConfigContext). **Entry points:** this page is the canonical paste flow; the cheat sheet header gets a "paste your .tmux.conf" affordance that deep-links here, and the existing prefix picker gains a "or paste your whole config →" hint.
6. **Surface-area pass**:
   - Cheat sheet rows whose `(table, key)` or normalized command differ from defaults get a "rebound" marker; **unbound** defaults render struck-through with an "unbound in your config" note (toggle-off restores).
   - Custom bindings whose normalized command matches **no dataset entry** (plugin bindings, `run-shell`, scripts) render in a new **"Your other bindings"** pane at the top of the cheat sheet — never dropped silently. `bind -n` customs group under a "no prefix needed" subheading there.
   - Palette matches custom keys; command pages show "your binding: X" when the normalized command matches but the key differs.

## Success Criteria

- For each of the 10 fixtures: correct prefix; ≥90% of **standard-table `bind` lines** are either overlaid onto a dataset entry (when the normalized command matches) or listed in "Your other bindings" — denominator = parseable `bind` lines in tables prefix/root/copy-mode-vi; zero errors thrown on any fixture.
- /config/explain: **manual review of all 10 fixtures finds zero incorrect annotations** (the r/tmux bar; human-judged, alongside automated fixture snapshots). Coverage target: every *parsed or recognized* line annotated; skipped lines grouped honestly with counts. The 300+ line `if-shell`-heavy fixture succeeds by *not lying* — correct annotations where it speaks, explicit "not annotated (N lines)" where it doesn't.
- The config generator's own output is fully accounted for on the explain page: every line it emits is parsed, recognized, or plugin-grouped — zero lines land in "couldn't read" (dev-time round-trip test).
- Config never leaves the browser (verifiable in devtools network tab — part of the launch post).
- Perf character of v1 unchanged (parser lazy-loaded; zero cost for visitors who never paste).
- Launch: r/tmux post survives contact with real configs (no correctness call-outs that survive a same-day fix); Show HN follows within ~2 weeks.
